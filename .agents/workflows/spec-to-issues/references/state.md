# Filing state and recovery

Use one private directory outside the repository, for example a new directory under the OS temporary directory, with mode 0700 and files mode 0600. Tell the person its absolute path. Keep it through delivery; resume needs it. Do not store state in a checkout or linked worktree, and never commit it. Lock the directory with exclusive creation before filing so two processes cannot resume the same run. Release the lock when done; after a crash, establish that its owner is no longer running before removing a stale lock.

Save state atomically (write a sibling temporary file, flush it, rename it). Use a versioned JSON snapshot with:

- Run UUID, repository, canonical spec path, SHA-256 of the whole spec bytes and label catalog, draft plan and triaged plan digests.
- Ordered drafts including ref, title, body, kind, parent ref, blocked-by refs, Size, Priority and labels, and a stable ref-to-number/id/URL mapping.
- Full triager report, policy line, per-node verdict/metadata, returned blocked-by edges with their reasons, and per-container groups, including ungrouped leaves. Persist the groups even when no record has been written yet.
- The person's confirmation, time, and exact confirmed plan digest. No confirmation for another digest is valid.
- Original and final rendered bodies and a journal of each intended operation, request payload digest, started/completed/uncertain state, response identifiers and verification evidence. Include post-create script invocations.

Before each remote write, persist its intent and deterministic operation key. After it returns, persist the response and verify by GET before marking complete. Pace all writes serially with at least one second between them; honor Retry-After and rate-limit reset responses. Stop on an unresolved ambiguous result. Never blindly retry a POST.

Issue creation includes a stable hidden marker `<!-- {{prefix}}spec-to-issues:<run-uuid>:<ref> -->` in its initial body. Save the intent and marker before sending the POST. Retain this marker in every body rewrite. On resume or a lost response, page the repository's issues (not search-index results alone) to find the exact marker and expected creator/repository, and adopt that issue into the saved map. Check that it matches the saved title and draft or final body. Zero matches after a possibly accepted POST is uncertain: do not POST again until a complete read establishes non-creation. Multiple matches stop recovery for human resolution. Never adopt an unrelated issue merely because its title matches. A duplicate search before first filing is read-only and may stop with an existing issue URL, but cannot authorize editing that issue.

Resume validates the schema, repository, source fingerprint, label fingerprint, plan digest and confirmation before any mutation. For the same unchanged plan, reuse the saved verdict and groups without spawning the triager again. Reconcile every journal entry with GitHub, including complete entries when external edits may have invalidated them. Refuse to overwrite unexpected human changes. GET existing sub-issues and blocked-by edges before adding them; when present in the expected direction, mark complete without another POST. For bodies and independence records, compare the desired content and markers before PATCH, replacing the run's record rather than appending a duplicate. Verify groups only name the owning container's direct leaf children. Resume must finish every record even if all issue creations completed before the interruption.

A changed spec, labels or triaged plan voids confirmation. Preserve the old journal, re-run pre-flight and triage, print the new tree and obtain new confirmation in a separate run before filing any changed plan. If earlier issues exist, report them and stop for an explicit reconciliation decision so a changed-spec run cannot duplicate or rewrite them. Never delete partially filed issues to start over.
